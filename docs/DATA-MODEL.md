# 数据模型：全局索引 + 分层聚合

> **定位：这是全局视图的插件。** 不是"点某个对话才加载某个对话"，而是**默认掌握全部数据**，
> 星海呈现的是「她这一路的全貌」，筛选和深入是视图层的操作，不是数据层的。
>
> 本插件是**观赏面**（见 `DATA-SOURCES.md` 第四节）：数据单向流入，不参与上下文。

---

## 一、实测规模，以及它逼出来的硬约束

```
cwd 目录      18 个
会话文件      49 个   session-<uuid>/session.v4.jsonl.zstd
压缩总量      74.7 MB
单会话最大     8.94 MB（压缩）→ 解压约 30–45 MB
```

zstd 约 4× → **原始 JSONL ~300 MB，事件量级 15 万 ~ 60 万**。

### 硬约束：索引可以全量，渲染必须分层

| | 60 万个点行不行 |
|---|---|
| **磁盘索引** | ✅ 可以。约 120 MB，可接受，也能随时删 |
| **一次性画到屏幕上** | ❌ 不行。不是性能调优能解决的：视觉上是一团糊，GPU 也画不动几十万条边 |

**所以「全局」的正确实现是：数据全量在手，视图按层级聚合。**

这跟 galaxy-view 的 cluster → node 是同一个思路，也是天文可视化的通行做法（LOD，Level of Detail）。

---

## 二、四层数据模型

```
cwd       18 个      ← 星系（工作目录天然分组）
  └ session  49 个   ← 星系里的恒星
      └ turn   几千个 ← 行星（一次问答）
          └ record 十几万条 ← 卫星（一条消息/一次工具）
```

**cwd 是最天然的一级簇**——本来就是按项目在聊，`--D-DeepSeek~0020Harness-123--` 这种目录名还原出来就是「123 项目」。所以星海可以有 18 个星系，每个星系里几十颗恒星，视觉上立刻成立。

### 2.1 session（会话）

```js
{
  id: "session-58c36733-…",
  cwd: "D:\\DeepSeek Harness\\123",     // → 决定它属于哪个星系
  title: "…",
  createdAt, updatedAt,
  turnCount: 87,
  recordCount: 4213,
  bytes: 3194.4,                         // 压缩文件大小，可当"重量"
  indexed: true                          // 是否已深度索引
}
```

### 2.2 turn（轮次）—— 全局一次性加载

```js
{
  id: "session-58c3…#12",
  sessionId, cwd,
  idx: 12,
  startedAt, endedAt,
  userLen, assistantLen, toolCount,
  weight                                   // 预计算
}
```

**为什么单独抽一层**：几千条 turn 一次全加载只要 ~800 KB，**LOD 0/1/2 就都能秒出全局视图**，不用碰十几万条记录。这一层是全局视图的主力。

### 2.3 record（记录）—— 按需，且全局时采样

```js
{
  id: "session-58c3…#12:3",
  sessionId, turnId, cwd,
  seq, t,
  kind: "user" | "assistant" | "tool" | "compaction",
  len, toolName, ok, durationMs,
  tokens: ["星海","three",…],   // 写入时分好词，渲染零成本
  weight
}
```

**全文不存**：需要时 `sessionQuery.readEvent(id)` 现取（宿主本来就存着）。

### 2.4 词索引

```js
// vocab.json：{ "星海": { n: 42, sessions: 3 }, "three": { n: 128, sessions: 7 } }
```

只收出现 ≥ 2 次的词，约 2–5 万条，3–5 MB。

## 三、LOD：四级深度 + 一层横向突触

| LOD | 画什么 | 点数 | 加载源 | 全局可用？ |
|---|---|---|---|---|
| **0 · 星系** | 18 个 cwd | 18 | `index.json` | ✅ |
| **1 · 会话** | 49 个会话 | 49 | `index.json` | ✅ |
| **2 · 轮次** | 几千个 turn | 1–5 千 | `turns.json` | ✅ 秒出 |
| **3 · 消息** | 十几万条 record | 1–5 万 | `records/*` | ⚠️ 需采样或筛选 |

**外加一层横向的「词突触」，它不在深度链上。**

词不是第 4 层，而是**公共连接器**：任何记录用到的词，就连到那个词节点。深探新的一簇时，如果发现共享的词，**立刻接线**——孤立的簇就这样连成一张网。

详见 `INTERACTION.md` 第五节。可以整体开关。

**默认打开是 LOD 1**（49 颗恒星分布成 18 个星系），一个滑杆调 0–3，或者直接点：
- 点星系 → 展开成它的会话
- 点恒星 → 展开成它的轮次
- 再往里 → 消息

这就是「深入层数」，做成滑杆最直观。

### LOD 3 的硬规则

十几万条 record 全画出来毫无意义（糊成一片，且 GPU 画不动那么多边）。所以：

- **全局 LOD 3** → **按 weight 分层采样**固定数量（默认 5000，可调 2000–20000）
- **筛选后 LOD 3** → 精确渲染（集合已经小了）
- **深探出来的 LOD 3** → 精确渲染（只有几十条）

采样用「按权重分层抽样」，保证重要的事不会漏，而不是随机抽。

## 四、筛选维度（视图层，不动数据）

| 维度 | 取值 | 字段 |
|---|---|---|
| **项目 / cwd** | 18 个目录，可多选 | `session.cwd` |
| **会话** | 49 个，可多选 | `sessionId` |
| **时间** | 全部 / 近 7 / 30 / 90 天 / 自定义 | `t` |
| **类型** | user / assistant / tool / compaction | `record.kind` |
| **工具名** | Bash / Read / Edit / … | `record.toolName` |
| **关键词** | 任意词，高亮含它的记录 | `record.tokens` |
| **权重下限** | 只看重要的事 | `record.weight >= x` |

**筛选是纯 client 侧数组过滤**——数据全在本地，不需要请求 host。

例：同时开「123 项目 + 近 30 天 + 只看 user 和 compaction」→ 从几万条筛出几百条，LOD 3 直接精确画。

## 五、存储布局

```
~/.dsh/plugins/dsh-memory-sea/store/
├── index.json          49 会话 + 18 cwd 元信息         ~30 KB    LOD 0/1
├── turns.json          全部轮次（几千条）              ~800 KB   LOD 2  ← 全局加载
├── vocab.json          全局词频                       3–5 MB    LOD 4
├── records/
│   ├── session-58c3….json   单会话记录              1–8 MB    LOD 3
│   └── … （49 个）
└── meta.json           版本、上次索引时间、统计
```

**启动加载顺序**：`index.json` → `turns.json` → **面板立即可用（LOD 0–2，全局视图）**。`vocab.json` 和 `records/*` 按需。

总量估计：30 KB + 800 KB + 4 MB + 49×2 MB ≈ **105 MB**，可随时整目录删除重建。

## 六、首次安装：全量索引，但不阻塞

既然定位是全局，**必须全量索引**。但 300 MB 解析 + 60 万条分词不能卡住启动。

### 时间估算

| 阶段 | 耗时 |
|---|---|
| 列会话 `listSessions()` | < 100 ms |
| 解压 + 解析 300 MB JSONL | 5–15 s |
| **分词 60 万条**（`Intl.Segmenter`） | **30–60 s** ← 瓶颈 |
| 写盘 | 2–3 s |
| **合计** | **1–2 分钟**（一次性） |

### 执行方式

```
① 立即：listSessions() → index.json
        面板立刻显示 49 颗恒星 + 18 个星系        <200 ms

② 后台：按「最近更新」倒序，逐个会话索引
        · 每个会话完成即写盘、通知 client 增量渲染
        · 每 200 条 / 每 2 秒让出主线程，不卡 UI
        · 面板显示「已索引 12/49，剩余约 40 秒」

③ 完成：写 meta.json，之后只做增量
```

**为什么不一次跑完再显示**：用户会以为卡死。渐进呈现（一颗一颗亮起来）反而**符合星海的气质**——像星星依次点亮。

### 分词是瓶颈，怎么削

- 只对 `len >= 20` 的文本分词（"好"、"继续"这种跳过）
- 长文本只取前 2000 字（后面的词频贡献有限）
- `Intl.Segmenter` 一次分段，不做二次处理
- 实测太慢就降级为「只对 `len >= 100` 的文本分词」，覆盖 80% 信息量

## 七、增量追加

### 触发

| 时机 | 动作 |
|---|---|
| 面板打开 | 追当前会话 |
| 面板打开期间 | 每 5 秒轮询 |
| `turn/end` | 立刻追（新的一轮完成） |

### 幂等

```js
const fresh = await sessionQuery.listEvents({ sessionId, after: lastSeq });
for (const ev of fresh) {
	const id = `${sessionId}#${ev.turn}#${ev.seq}`;   // 稳定 id
	if (seen.has(id)) continue;                        // 去重
	addRecord(toRecord(ev));
	lastSeq = Math.max(lastSeq, ev.seq);
}
```

追加时**同步更新三处**：`records/<id>.json`、`turns.json`、`vocab.json`。

攒 200 条或每 10 秒落盘；崩溃最多丢 10 秒增量，可从宿主重建。

## 八、多视图 = 同一份数据的派生物

存储只有一份，视图全是派生：

| 视图 | 数据源 | 边 | 大小 | 颜色 |
|---|---|---|---|---|
| **按项目** | cwd 分组 | 项目↔会话 | 会话数 | 项目 |
| **按对话** | sessionId | 同轮 + seq 邻接 | `turn.weight` | 会话 / cwd |
| **按时间** | `t` 排序 | 时间邻接 | `record.weight` | `kind` |
| **按类型** | `kind` 分簇 | 同类型 + 原始邻接 | `record.weight` | kind 固定色 |
| **按词频** | words ↔ records 二部图 | 词-消息 | 词 `vocab.n` / 消息 `weight` | 词一色，消息按 kind |
| **按轮次** | `turns` | 轮次顺序 | `turn.weight` | 会话 |

**新增一种视图 = 加一个 `buildXxx()`，不动存储。** 这是这套结构的核心价值。

## 九、容量与性能预算

| 项 | 预算 |
|---|---|
| 启动到出画面（LOD 0–2 全局） | **< 300 ms**（index + turns，< 1 MB） |
| 首次全量索引 | 1–2 分钟（后台，渐进显示） |
| 增量追加 | < 100 ms |
| 切换 LOD | < 200 ms（LOD 3 可能 0.5–1 s） |
| 筛选 | < 50 ms（纯数组过滤） |
| 存储总量 | ~105 MB，可随时删 |

## 十、待定的设计选择（需要讨论）

1. **默认 LOD 起点**：1（49 颗会话星）还是 2（几千个轮次）？前者清朗，后者更有"海"的感觉。
2. **LOD 3 全局采样数量**：5000 够不够？采样用「按权重分层」还是「按时间均匀」？
3. **cwd 星系是否合并冷门**：18 个目录里有几个是临时的（`测试`、`新建文件夹`），要不要按活跃度隐藏？
4. **词频视图词数上限**：200 / 500 / 1000？
5. **首次索引**：「装完自动跑」还是「等用户点开始」？前者装完即有全貌，后者不打扰。
6. **是否保留"只看当前会话"快速筛选**：全局是默认，但当前会话可能仍是最常看的那个。
